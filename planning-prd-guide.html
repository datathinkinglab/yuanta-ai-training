지점장 교육 · 19페이지 참고자료

아이디어를 기획서로,
기획서를 PRD로 구체화하기

만들기 전에 목적과 완성 기준을 정하면, AI에 요청할 내용과 결과를 확인할 기준이 분명해집니다.

두 문서의 차이요구사항 예시기획서 프롬프트PRD 프롬프트검토와 개발 연결

1. 기획서는 목적, PRD는 구현·검증 기준

기획서: 왜, 누구를 위해 만드나요?

해결할 업무 문제와 웹앱의 방향을 합의하는 문서입니다. 지점장이 어떤 판단이나 행동을 더 잘하도록 도울지 설명합니다.

  • 현재 문제와 확인된 근거
  • 목표 사용자와 사용 상황
  • 개선 후 업무 흐름과 핵심 기능
  • 첫 버전의 범위와 제외할 기능
  • 성공 판단 지표와 확인할 사항

PRD: 무엇을, 어떻게 동작하게 만드나요?

Product Requirements Document. 이 강의에서는 개발에 전달할 요구사항정의서로 사용합니다. 기능·데이터·화면 동작과 완료 판정 조건을 구체화합니다.

  • 사용자 역할과 사용 시나리오
  • 기능별 입력 → 동작 → 결과
  • 화면 구성과 데이터 항목·계산식
  • 누락·오류·빈 화면 처리
  • 우선순위와 수용 기준(통과 조건)
작성 순서: 업무 아이디어 → 기획서 초안 → 지점장 검토 → PRD 초안 → 요구사항 확정 → 웹앱 개발 → PRD 기준으로 확인.
두 문서를 길게 쓰는 것보다, “무엇을 만들고 언제 완성으로 볼지”를 명확히 쓰는 것이 핵심입니다.

2. 지점장 코칭 대시보드로 비교해 보기

교육용 가상 사례입니다. 실제 업무의 불편이나 개선 효과가 검증되었다는 뜻은 아닙니다.

문서작성 예시
기획서지점장이 면담 전 직원별 실적과 최근 추이를 한 화면에서 확인하고, 면담에서 확인할 질문을 준비하도록 돕는다. 첫 버전은 가상 CSV 기반 조회용 대시보드로 만든다.
PRD · 기능 F-01입력: 가상 CSV와 직원 선택.
동작: 선택한 직원의 최신 월 약정·제공된 6개월 평균·월별 추이를 표시한다.
예외: 필수 열이 없으면 누락된 열을 안내하고, 미입력 수치는 0으로 바꾸지 않는다.
PRD · 수용 기준직원 A를 선택하면 A의 값만 표시된다. 기준월 값이 120, 제공된 6개월 평균이 100인 가상 검증값에서는 변화율이 +20%다. 평균이 0이거나 값이 없으면 ‘비교 불가’다.

추상적인 표현 바꾸기: “보기 좋게 만들어 주세요” → “직원 목록에서 한 명을 선택하면 해당 직원의 수치·추이가 함께 바뀌고, 기준월과 단위를 표시해 주세요.”

3. 기획서 작성 프롬프트 템플릿

대괄호 [ ]를 내 업무에 맞게 채운 뒤 복사하세요. 16페이지에서 정리한 사용 목적과 19페이지의 첫 요청문을 재료로 활용할 수 있습니다.

1단계 · 업무 아이디어 → 기획서 초안
당신은 업무용 웹앱 기획을 돕는 서비스 기획자입니다.
아래 내용을 바탕으로 비개발자인 지점장이 검토할 수 있는 1~2쪽 분량의 웹앱 기획서 초안을 작성해 주세요. 지금은 코드를 작성하지 마세요.

[기획 입력]
• 웹앱 이름: [예: 영업직원 코칭 대시보드]
• 사용자와 사용 상황: [누가, 언제, 어떤 판단을 위해 사용하는지]
• 현재 업무와 불편: [지금 하는 일과 해결하고 싶은 문제]
• 확인된 근거: [관찰·자료 / 없으면 ‘확인 필요’]
• 원하는 변화: [앱을 사용한 뒤 할 수 있어야 하는 일]
• 사용할 교육용 가상 데이터: [파일 형식, 열 이름, 기간, 단위]
• 꼭 필요한 기능 3~5개: [파일 불러오기, 필터, 직원 선택 등]
• 첫 버전에서 제외할 기능: [예: 실제 고객정보 연동, 자동 인사평가]
• 실행 환경과 제약: [예: PC 브라우저, 단일 HTML, 서버 없이 실행]
• 성공 판단 기준: [예: 선택 직원의 수치·추이를 원자료와 대조할 수 있음]

[기획서 구성]
1. 한 문장 요약과 업무 문제
2. 대상 사용자와 사용 목적
3. 현재 업무 → 개선 후 업무 흐름
4. 첫 버전의 핵심 기능과 제공할 가치
5. 포함 범위 / 제외 범위
6. 필요한 데이터와 취급 원칙
7. 성공 판단 지표와 확인 방법
8. 미확정 사항과 지점장에게 확인할 질문

[작성 원칙]
사실·가정·확인 필요를 구분하고, 근거 없는 효과나 목표 수치를 만들지 마세요.
실명·고객정보·내부 미공개 자료 대신 가상 자료만 사용하는 교육용으로 기획하세요.
중요한 정보가 빠졌으면 먼저 핵심 질문을 최대 5개 제시하고 답을 기다리세요.
추가 아이디어는 ‘제안’으로 표시하고 첫 버전의 확정 기능과 구분하세요.

4. PRD(요구사항정의서) 작성 프롬프트 템플릿

앞 단계에서 작성하고 직접 검토한 기획서를 붙여 넣으세요. 기능마다 “어떤 입력에서 어떤 결과가 나오면 통과인지”까지 요청합니다.

2단계 · 검토한 기획서 → PRD 초안
당신은 업무용 웹앱의 요구사항을 정리하는 제품 기획자입니다.
아래 기획서를 바탕으로 AI 개발 도구에 전달할 PRD(요구사항정의서)를 한국어로 작성해 주세요. 지금은 코드를 작성하지 마세요.

[지점장이 검토한 기획서]
[여기에 검토한 기획서 전문을 붙여 넣으세요]

[데이터 정의 또는 가상 샘플]
[열 이름, 데이터형, 단위, 기간, 가상 샘플을 붙여 넣으세요]

[PRD 구성]
1. 제품 목적, 사용자 역할, 사용 시나리오
2. 첫 버전의 포함 범위와 제외 범위
3. 화면 구성과 사용 흐름: 첫 화면 → 데이터 입력 → 필터 → 직원 선택 → 결과 확인
4. 기능 요구사항 표:
   요구사항 ID | 기능 | 우선순위(필수/선택) | 입력·전제조건 | 사용자 동작 | 표시 결과 | 누락·오류 처리 | 수용 기준
5. 데이터 정의: 열 이름, 데이터형, 필수 여부, 단위, 기준월, 검증 규칙
6. 계산·표시 규칙: 계산식, 비교 기준, 반올림, 필터 적용 범위
7. 실행 환경, 외부 연결 여부, 데이터 보관·초기화 방식, 개인정보 취급 원칙
8. 검증 시나리오 표: 요구사항 ID | 테스트 입력 | 조작 | 기대 결과
9. 미확정 사항과 확인 질문

[코칭 대시보드의 확인 조건]
• 기준월은 인식된 월 중 최신 월로 정하고 화면에 표시하세요.
• ‘제공된 6개월평균약정’을 이용한 변화율은
  (기준월 약정−제공된 6개월 평균)÷제공된 6개월 평균×100으로 정의하세요.
• 평균이 0이거나 필요한 값이 없으면 ‘비교 불가’로 표시하고, 누락값을 0으로 대체하지 마세요.
• 월별 추이, 순위, 단위는 제공된 데이터 정의를 따르고 없는 값은 추정하지 마세요.
• 파일 미입력, 필수 열 누락, 필터 결과 없음, 직원 선택 변경도 검증 항목에 포함하세요.
• 검증용 가상 값 120과 100에서는 변화율이 +20%인지 확인하도록 작성하세요.

[작성 원칙]
기획서가 없으면 먼저 입력을 요청하고 PRD를 임의로 만들지 마세요.
기획서와 데이터 정의가 충돌하거나 단위·계산·저장 방식이 미정이면 ‘확인 필요’로 남기고 질문하세요.
추가 기능은 제안으로 구분하고, 사용자가 확정하기 전 필수 범위에 넣지 마세요.
실제 고객정보 연동·자동 평가·외부 전송은 승인된 요구사항인 것처럼 포함하지 마세요.
실행하지 않은 테스트를 ‘통과’로 표시하지 마세요.

5. 검토한 뒤 개발 요청으로 연결하기

  1. 기획서 검토: 실제 해결할 문제인가? 대상 사용자·첫 버전·제외 범위가 분명한가?
  2. PRD 검토: 화면 동작·데이터 정의·계산식·예외 처리에 모호한 부분이 없는가?
  3. 완료 기준 확인: 정상값·누락·0·필터 결과 없음을 직접 확인할 수 있는가?
  4. 개발 요청: 검토한 PRD를 AI에 전달하고, 생성된 웹앱을 요구사항별로 확인한다.

19페이지에서는 나의 첫 요청문을 먼저 작성해 보세요. 이 가이드는 요청을 더 구체화하는 보충자료입니다. 다음 20페이지의 공통 생성 프롬프트와 비교하며 빠진 조건을 확인할 수 있습니다.

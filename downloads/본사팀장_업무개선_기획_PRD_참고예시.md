# 본사 팀장 교육 — 업무 개선안·웹앱 기획서·PRD 참고 예시

모듈 4 기존 대시보드 실습과 별도로 보는 선택 참고자료입니다.

## 1. 출발점: 업무 개선안

업무 개선안 1장 — 주간 자료 취합·검토 인계

교육용 가상 사례입니다. 실제 유안타증권의 절차·규정·성과를 진단한 내용이 아닙니다.

1. 업무와 범위
주간 보고자료의 요청 접수부터 검토자 인계까지를 개선 대상으로 삼는다. 인계 후 내용 검토와 최종 보고는 사람이 수행한다.

2. AS-IS 분석 결과
현재 흐름: 요청 접수 → 자료 취합 → 검토 중 누락 발견 → 보완 재요청·대기 → 검토·보고.
문제 A: 자료 누락을 검토 단계에서 발견해 되돌아가기와 대기가 발생한다.
문제 B: 필수자료가 빠진 상태에서도 검토자에게 자료가 전달될 수 있다.
원인 가설: 접수 직후 확인 절차와 검토 인계 기준이 불명확할 수 있다.
근거 상태: 교육용으로 가정한 상황. 현업에서는 보완 요청 이력·누락 발견 시점·인계 시점으로 확인해야 한다.

3. 변경 내용과 TO-BE
A → 확인 시점을 접수 직후로 앞당긴다. 담당자가 필수자료 유무를 먼저 확인한다.
B → 인계 기준을 명시한다. 누락이면 보완을 요청하고, 자료 충족 확인 후 검토자에게 전달한다.
TO-BE: 요청 접수 → 필수자료 확인 → 누락 시 보완·재확인 → 충족 후 검토 인계 → 내용 검토·보고.
자료 유무 확인과 내용의 정확성·승인은 구분한다.

4. 책임과 AI 지원
접수 담당: 자료 유무 확인, 보완 요청, 보완 후 재확인, 인계 기록.
팀장: 필수자료 기준 검토, 내용·예외·우선순위 판단.
AI: 확인 목록·보완 요청 문안 초안 작성 지원. 담당자가 검토한다.

5. 시범 적용과 확인
가상 적용 제안: 동일한 종류의 요청을 정해 적용 전후 검토 단계 재요청 횟수와 대기시간을 비교한다. 대상·기간·기록 책임은 현업 협의가 필요하다.
기대 효과: 검토 단계의 되돌아가기 감소. 실제 효과는 미측정이다.

6. 필요한 결정
필수자료 목록, 예외 승인 기준, 보완 요청 방식, 기록 보관·접근 권한을 확인한다.

## 2. 참고용 웹앱 기획서

참고용 웹앱 기획서 — 접수 자료 확인·검토 인계 도우미

교육용 독립 예시. 모듈 4의 기존 대시보드 실습과 가상 8건 데이터는 그대로 진행한다. 이 기획서는 모듈 2·3 산출물을 나중에 웹앱으로 확장하는 방법을 보여준다.

1. 기획 목적
업무 개선안의 ‘접수 직후 자료 확인’과 ‘자료 충족 후 검토 인계’를 작은 화면으로 지원한다. 업무 전체를 자동화하는 대신 담당자의 확인과 다음 조치를 돕는다.

2. 사용자와 사용 장면
접수 담당은 새 요청의 필수자료 유무를 확인하고 보완할 항목을 찾는다. 팀장은 확인 상태·대기 사유를 살펴보고 예외와 지원 필요를 판단한다.

3. 분석 결과에서 화면 기능으로
문제 A: 검토 중 누락 발견 → 접수 직후 확인 → 필수자료 체크와 미확인 표시 → REQ-01.
문제 B: 불완전한 자료 인계 → 자료 충족 후 인계 → 확인 상태에 따른 인계 가능 표시와 수동 인계 기록 → REQ-02·03.
지원할 행동: 보완 필요와 다음 조치를 파악 → 요청별 담당·마감·보완 메모·상태를 목록으로 조회 → REQ-04.

4. 화면과 입력
상단: 교육용 가상 자료·자동 승인 아님·저장 범위 안내.
목록: 요청 ID, 제목, 담당, 마감, 자료 확인 상태, 인계 상태, 다음 조치.
상세: 필수자료별 확인값, 보완 메모, 수동 인계 기록 버튼.
필수자료 3종(교육용): 요청 개요, 비교표, 근거자료. 실제 목록은 현업에서 확인한다.

5. 업무 흐름
담당자가 요청 선택 → 필수자료 확인 → 미확인 항목이 있으면 ‘보완 필요’ → 자료 보완 후 재확인 → 모두 확인하면 ‘인계 가능’ → 담당자가 별도로 인계 기록 → 팀장이 내용 검토.
‘인계 가능’은 자료 유무에 대한 안내이며 내용의 정확성·검토 완료·승인을 뜻하지 않는다.

6. 범위와 제약
단일 HTML·교육용 가상 자료·브라우저 메모리에서 실행하는 독립 참고 예시다. 새로고침하면 초기화한다.
실제 첨부파일 업로드·메일 발송·자동 승인·계정·권한·공동 저장은 제외한다. 역할 표시는 실제 접근 통제를 제공하지 않는다.
이 예시의 상태·자료·검증값은 모듈 4의 기본 8건 및 지표와 별개다.

7. 완성 기준
정상·누락·보완 후 인계·인계 후 자료 재변경 시나리오가 PRD의 수용 기준에 맞게 동작한다. 예시를 작성했다는 사실은 개발·검증 완료를 뜻하지 않는다.
현업 개선 효과는 별도의 기록으로 측정한다. 체크 항목 입력 여부만으로 재요청 감소를 주장하지 않는다.

8. 확인이 필요한 사항
필수자료 정의, 예외 처리 권한, 실제 자료 보관 방식, 개인정보·접근 통제·연계 방식, 효과 측정의 시작·종료 기준.

## 3. 참고용 PRD

참고용 PRD — 접수 자료 확인·검토 인계 도우미

입력 문서: 위 참고용 웹앱 기획서. 목적은 기획서의 개선 방향을 개발·검증 가능한 조건으로 구체화하는 것이다. 아래 내용은 제안이며 실제 사내 규정이 아니다.

1. 데이터와 상태 정의
요청: id, title, owner, dueDate, materials, followUpMemo, handoffRecorded.
materials: 요청 개요·비교표·근거자료 각각 ‘미확인/확인’ 두 값. 원문과 파일은 보관하지 않는다.
자료 충족 = 필수자료 3종이 모두 ‘확인’인 경우.
handoffRecorded는 담당자가 인계 사실을 기록했는지 나타내며 초기값은 false.
표시 상태: 미충족이면 ‘보완 필요’, 충족·미인계면 ‘인계 가능’, 충족·인계 기록이면 ‘인계 기록됨’.
마감 미입력은 ‘기한 확인 필요’로 표시하며 임의로 지연으로 분류하지 않는다.

2. 기능 요구사항과 수용 기준

REQ-01 | 필수자료 확인
근거: 문제 A → 접수 직후 자료 유무 확인.
동작: 담당자가 자료별 확인값을 바꾸면 자료 충족 여부와 다음 조치를 다시 표시한다. ‘미확인’은 실제 자료 부재가 확정됐다는 뜻이 아니다.
수용 기준: 하나라도 미확인이면 ‘보완 필요’와 미확인 자료명이 표시되고, 모두 확인하면 ‘인계 가능’으로 바뀐다.

REQ-02 | 인계 가능 조건과 예외 안내
근거: 문제 B → 자료 충족 후 검토 인계.
동작: 미충족 상태에서 인계 기록 버튼을 누르면 기록을 막고 미확인 항목을 안내한다. 담당자는 보완 메모를 작성할 수 있다.
수용 기준: 메모만 작성해도 인계 가능으로 바뀌지 않는다. 예외 인계가 필요하면 팀장 판단 필요를 안내하며 이 예시에서는 예외 승인 기능을 제공하지 않는다.

REQ-03 | 수동 인계 기록과 재확인
근거: 인계 가능 표시와 실제 인계 행동을 분리.
동작: 자료 충족 시 담당자가 버튼을 눌러 인계 사실을 기록한다. 실제 전송은 수행하지 않는다.
수용 기준: 모두 확인으로 바꾼 것만으로 인계 기록됨이 되지 않는다. 인계 후 자료를 미확인으로 바꾸면 handoffRecorded를 false로 되돌리고 재확인 필요 안내와 보완 필요 상태를 표시한다.

REQ-04 | 목록·필터·다음 조치
근거: 개선 흐름에서 담당자가 확인·보완·인계할 건을 찾도록 지원.
동작: 전체/보완 필요/인계 가능/인계 기록됨 필터를 제공한다. 목록에 담당·마감·다음 조치를 표시한다.
수용 기준: 상태 변경 시 현재 필터에 맞춰 목록을 즉시 갱신한다. 빈 결과에는 ‘해당 요청 없음’을 표시한다. 필터는 자료 자체를 삭제하거나 상태를 변경하지 않는다.

3. 검증용 가상 자료 — 모듈 4의 8건과 별개
R01: 요청 개요=확인, 비교표=확인, 근거자료=확인, 인계 기록=false → 인계 가능.
R02: 요청 개요=확인, 비교표=미확인, 근거자료=확인, 인계 기록=false → 보완 필요.
R03: 필수자료 모두 미확인, 마감 없음, 인계 기록=false → 보완 필요·기한 확인 필요.
초기 상태 예상: 전체 3건, 보완 필요 2건, 인계 가능 1건, 인계 기록됨 0건. 기대값이며 실제 검증 결과가 아니다.

4. 검증 시나리오
T01 / REQ-01: 초기 자료를 열고 세 요청의 상태와 미확인 자료명을 대조한다.
T02 / REQ-02: R02의 인계 기록을 시도한다 → 차단·비교표 미확인 안내, 인계 기록=false 유지.
T03 / REQ-01·03: R02 비교표를 확인으로 바꾼다 → 인계 가능. 수동 기록 버튼을 누른 뒤에만 인계 기록됨.
T04 / REQ-03: T03 후 R02 근거자료를 미확인으로 변경한다 → 인계 기록 초기화·보완 필요·재확인 안내.
T05 / REQ-04: ‘인계 가능’ 필터에서 R01을 인계 기록한다 → 현재 목록에서 제외. 마지막 건이었으면 빈 결과 안내.
T06 / 범위: 새로고침한다 → 3건 초기 상태 복원·초기화 안내. 실제 발송·승인·공동 저장을 수행한 것처럼 표시하지 않는다.
각 시험은 독립 실행 시 초기 자료로 되돌린다. T03·04만 순서대로 수행한다. 실제 결과·오류·미검증 여부는 개발 후 별도로 기록한다.

5. 개발 전달 조건
기획서와 PRD를 함께 전달하고 단일 HTML 전체 코드 및 위 시험 절차를 요청한다. 필수자료·예외 기준을 실제 사내 기준으로 단정하지 않는다. 이 예시를 위해 모듈 4의 기존 대시보드 코드를 변경할 필요는 없다.

## 4. 개발에 활용할 때

위 참고용 기획서와 PRD를 근거로 교육용 독립 웹앱을 단일 HTML로 작성해 주세요.
모듈 4의 기존 대시보드·가상 8건·계산 규칙과 별개의 예시로 만드세요.
REQ-01~04와 R01~03 초기 자료, T01~06 검증 절차를 유지하세요. 외부 라이브러리·서버·API 없이 실행하고 새로고침 시 초기화하세요.
실제 승인·발송·첨부 보관·공동 저장·접근 통제가 구현된 것처럼 표시하지 마세요.
불명확한 사항은 질문하거나 확인 필요로 남기고, 코드 뒤에 요구사항별 구현 위치와 검증 방법을 설명하세요. 실행하지 않은 시험을 통과했다고 쓰지 마세요.
